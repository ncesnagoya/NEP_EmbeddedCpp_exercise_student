# 補足教材（オプション）：モダンC++で書く binary_file

step1・step2 では、コピー禁止を **private**、ファイルの後始末を **デストラクタ** で実装しました。
これは C++03 までの定石ですが、**C++11 以降の実務では別の書き方が標準** になっています。
このオプション演習では、同じ binary_file を次の2点でモダンな書き方に置き換えます。

1. コピー禁止を `private` ではなく **`= delete`** で表現する
2. `FILE*` を **`std::unique_ptr`（スマートポインタ）** で管理し、デストラクタを書かずに自動で `fclose` する（RAII）

> このステップは step1・step2 を終えた人向けの **発展（自習推奨）** です。
> 既存の演習を変更するものではなく、「現在の実務ではこう書く」を知るための補足です。
> 「３発展的な話題」のスライドで触れた `nullptr`・`override`・スマートポインタの実例にもなっています。

## 1. なぜ private より `= delete` なのか

step1 の演習3では、コピーコンストラクタを `private` に置いてコピーを禁止しました。
この方法には弱点があります。

- クラスの**内部や friend からは呼べてしまう**（完全な禁止ではない）
- 宣言だけして定義しないため、誤って呼ぶと **リンク時** まで間違いに気づけない
- 「禁止したい」という意図がコードから読み取りにくい

C++11 の `= delete` はこれらを解決します。

```cpp
// C++03（旧）: private に置いて定義しない
private:
  binary_file(const binary_file&);

// C++11（新）: = delete で明示的に禁止
public:
  binary_file(const binary_file&) = delete;
  binary_file& operator=(const binary_file&) = delete;
```

`= delete` されたコピーを呼ぶと、**コンパイル時** に
`use of deleted function` という明確なエラーになります。意図も一目で伝わります。

## 2. なぜ unique_ptr（RAII）なのか

step1 では、コンストラクタで開いたファイルをデストラクタで閉じました。
これは **RAII（Resource Acquisition Is Initialization）** という考え方そのものです。
「確保したら、寿命の終わりに必ず解放する」を、デストラクタに任せる仕組みです。

C++11 の **`std::unique_ptr`** を使うと、この後始末を自分でデストラクタに書かなくても、
ポインタが破棄されるタイミングで自動的に行われます。
`FILE*` のように `delete` ではなく `fclose` で閉じたい場合は、**カスタム削除子** を渡します。

```cpp
// FILE* を閉じる「削除子」
struct file_closer {
  void operator()(std::FILE* fp) const {
    if (fp) std::fclose(fp);
  }
};

// FILE* の所有権を持つスマートポインタ
std::unique_ptr<std::FILE, file_closer> stream_;
```

こうすると、

- **デストラクタを書く必要がない**（`unique_ptr` が破棄時に自動で `fclose`）
- **二重 close や close 忘れが起きにくい**
- `unique_ptr` はコピーできないので、**コピー禁止が自然に実現**される（所有権は1つだけ）
- **ムーブ**（`std::move`）で所有権を安全に移動できる

生の `FILE*` は `stream_.get()` で取り出して `fwrite` などに渡します。

## 4. 組込みで使うときの注意

スマートポインタは便利ですが、組込み開発では使いどころに注意が必要です。

- **動的メモリ確保そのものへの制約**：
  `std::shared_ptr` は参照カウント用に内部でヒープを使います。MISRA C++ や AUTOSAR の
  ガイドラインでは、動的メモリ確保を制限・禁止する場面があります。今回の `std::unique_ptr` は
  **追加のヒープ確保をしません**（ポインタ1つ分のサイズで、削除子も状態を持たないため）。
  組込みで使うなら、まず `unique_ptr` を第一候補にし、`shared_ptr` は所有権の共有が
  本当に必要なときに限定するのが定石です。
- **例外**：`unique_ptr` 自体は例外を投げませんが、RAII は例外が飛んでも確実に後始末される
  という点で、例外を使う設計とも相性が良い仕組みです。
- **`unique_ptr` のオーバーヘッド**：状態を持たない削除子なら、`unique_ptr` は生ポインタと
  同じ大きさ・同じ実行コストになります（ゼロオーバーヘッド）。安心して使えます。

> まとめ：`= delete` と `unique_ptr`（RAII）は、step1・step2 で手書きした
> 「コピー禁止」と「デストラクタでの後始末」を、より安全・簡潔に書き直したものです。
> 現在のC++（MISRA C++:2023 / AUTOSAR C++14 が対象とする C++14〜17）では、こちらが標準的な書き方です。
